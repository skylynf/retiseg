一、协作规则（不变，2026-10-14 定）
  1. 服务器只执行仓库 HEAD 里的本文件；聊天里的话与 HEAD 不一致时停下，等下一次 pull。每做完一项在 docs/ops/00_进度.txt 第三节追加一行（日期、提交号、卡、目录、刚落盘的指标文件名和 mAUPR）；14、13、CHECKPOINT、论文由本机在 collect_runs 之后改。
  2. 一个启动器、一份队列文件：bench/scripts/launch_queue.py 读 bench/configs/queue.yaml，优先级写在文件里，每次有空卡就重读；改顺序只改文件并提交，不杀进程。正在跑的旧启动器（launch_e3a、launch_factor、nnunet 脚本）让它们自然结束，新启动器跳过它们正在跑的目录（console.log 的 == start / == exit）。
       RETISEG_GPUS="<卡>" bash bench/scripts/server_run.sh queue      # 或 python bench/scripts/launch_queue.py 只打印计划
     新阶段类型（e5_infer）要求用含该代码的提交重启启动器；旧进程只会把它报成 unknown kind 并跳过。
     "一个"是指同一台主机上只有一个 launch_queue 进程，把所有要用的卡都写进 RETISEG_GPUS（被占的卡它会等，空出来就接）；几张卡各开一个启动器会同时规划同一项（2026-10-15 三个启动器同一分钟打开了 runs/E3a/BS_fct_idrid_seed1/FGADR）。2026-10-15 起启动器在开始一项之前先在目录里原子地写 claim.json（第二个启动器写不进就跳过），这只是兜底，不改变一台主机一个启动器的规则。
  3. 评测在训练结束时直接带冻结的排除名单写出 metrics_test.json（launch_factor.evaluate_argv、nnunet_run.sh、bench.e3a 都已如此）。excluded_ids 没对齐的指标：不写进 14，pack_handoff.py 不打包，collect_runs.py 拒收。
  4. CPU 步骤都是可单条重跑的命令（bench.e5 各模块的命令行、launch_factor.py --score-only 打印的 evaluate、nnunet_bridge.py 的 convert/splits/info、prepare_datasets.py export），不写总脚本。
  5. 本机写回后由用户提交推送；服务器 pull 到的提交号写进 00 的状态行。

二、回传格式
  python bench/scripts/pack_handoff.py [--since runs/handoff_manifest_<上次日期>.tsv]
  打进包的：runs/ 下的 json、jsonl、yaml、log、txt、tsv、md 和 done.json 等标记（单个 ≤8 MB）；summary/scored_metrics.tsv、summary/new_since.tsv（给了 --since 时）、summary/unaligned.tsv、manifest.tsv、snapshot/。不进包的：npz、pt、pth、png、prob_*/、masks/、nnunet 的 raw/preprocessed/pkl。排除名单没对齐的指标文件只列在 unaligned.tsv。
  另附：dataset/prepared/MAPLES-DR/report.json、runs/audit/leak_maples.json（第十节）、runs/E5/selection_*.json（第七节）。
  本机收到后：解入 runs/，python docs/paper/retiseg_paper/paper/scripts/collect_runs.py，make -C docs/paper/retiseg_paper/paper。
