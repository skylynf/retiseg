服务器执行手册（第一批，2026-10-07 起）

命令都在 bench/scripts/server_run.sh 里，按阶段调用。本文件说明顺序、每一步之后看什么、记在哪里。本机内存只有 30GB，本机不跑训练，也不跑真实网络的前向；只做单元测试和打印任务表。

一、准备（每台服务器一次）
1. 代码
   git clone git@github.com:skylynf/retiseg.git && cd retiseg
   git submodule update --init official_code/M2MRF official_code/HACDR-Net official_code/H2Former \
     official_code/HRNet-Semantic-Segmentation official_code/Swin-Unet official_code/FCT
   只初始化包装器会导入的这几个子模块。tensorflow/models、caffe 等很大，又用不到，不要用 --recursive。
2. 从工作站拷数据和权重（这些都不在 Git 里），在工作站上执行，SERVER 换成服务器地址，路径换成服务器上的仓库目录：
   rsync -a --info=progress2 dataset/prepared dataset/iDRID SERVER:retiseg/dataset/
   rsync -a pretrained SERVER:retiseg/
   rsync -a runs/E1_m2mrf SERVER:retiseg/runs/
   dataset/prepared 约 0.7GB，dataset/iDRID 约 1.5GB（只有 E1r 读原始 IDRiD），runs/E1_m2mrf 含 HRNet-W48 ImageNet 权重和两份作者权重。
   2026-10-07 起 dataset/prepared 另有 TJDR_std、TJDR_uwf、FGADR、DiaRetDB1、RetinalLesions，合计约 10GB。已经同步过 IDRiD、DDR 的话，只补新目录即可，rsync 会跳过没变的文件：
     rsync -a --info=progress2 dataset/prepared/ SERVER:retiseg/dataset/prepared/
   FGADR 和 Retinal-Lesions 的许可只允许研究使用、不得再分发：只放在项目自己的服务器上，不放进共享盘或公开存储，它们的概率图同样不外传。
   服务器不需要原始 zip；新库的导出和名单核对都在工作站上做。
3. bash bench/scripts/server_run.sh env
   建 retiseg（PyTorch 2.x，CUDA 12）和 retiseg-hacdr（PyTorch 1.10，CUDA 11.3，mmcv-full 1.6.2）。两个环境都要打印出自检行，M2MRF 要打印 “builds in retiseg”。
4. bash bench/scripts/server_run.sh check
   检查数据和权重，列出 GPU，下载一次 torchvision 的 ResNet-101 和 ResNet-34 ImageNet 权重，然后在两个环境里跑测试。测试不全过就停下，把输出发回来。
5. bash bench/scripts/server_run.sh cache
   建 IDRiD 和 DDR 的 1440 画布缓存，在 dataset/cache 下。源文件变了会报错，重跑这一步即可。

二、冒烟
6. bash bench/scripts/server_run.sh smoke
   B1 的 16 个任务跑完，再跑 B-std 的 16 个，每个 20 步，都只用训练集和验证集，目录在 runs/smoke。
   看：每个任务的 console.log 最后一行是 “== exit 0”；记下显存峰值（nvidia-smi）和每步耗时。显存不够的模型，在它的 cell 里加 batch_size（必须能整除有效批），用梯度累积补足；改动提交后再进入下一步。
   只重跑个别模型：bash bench/scripts/server_run.sh resmoke M2MRF,H2Former（B1 和 B-std 各跑一遍，只跑这几个模型）。
   2026-10-07 第一次冒烟：28/32 通过；M2MRF B1 改成批 2 累积到 4，H2Former 加了激活重计算，待 resmoke 确认。

三、并行的第一轮（三件事互不依赖，可以同时开）
7. bash bench/scripts/server_run.sh probe          占 GPU 0–3（PROBE_GPUS 可改）
   U-Net 和 M2MRF 在 IDRiD、DDR 上以两倍暂定预算各跑一次种子 0，只训练和验证。目录 runs/BSprobe_*。
8. bash bench/scripts/server_run.sh e1r            占 GPU 4（E1R_GPU 可改）
   M2MRF 作者配方重训，有效批 4，4 万步，目录 runs/E1r_m2mrf_idrid_seed0_bs4_a100。本机那次在第 1120 步中断，不续。中断后再执行同一命令，会从 last.pt 接着跑。
9. RETISEG_GPUS="5 6 7" bash bench/scripts/server_run.sh b1-seed0
   B1 种子 0，16 个任务，只训练和验证。B1 的预算不取决于探测结果，可以先跑。
   启动器开始时只取空闲的卡；RETISEG_GPUS 再把范围限制在 5–7，避免 probe 刚启动、还没占上卡时被抢。
   空闲指该卡上计算进程占用的显存合计少于 RETISEG_BUSY_MIB（默认 2048）。别人只留一个闲置的 CUDA 上下文（约 0.5GB）时，这张卡照样能用；跑着训练或模型服务的卡不会被拿走。
   2026-10-08 起 B1 暂停，这一步先不做，见 00。

四、定预算，再跑主表
10. bash bench/scripts/server_run.sh curves 'BSprobe_*'
    看每条曲线的验证 mAUPR，先做居中 3 点滑动平均（每个点取它和前后各一次验证的平均，两端只有 2 个点就取 2 点平均），再找平滑后最高点所在的步数。每个数据集单独判断：该库任一条探测曲线平滑后的最高点不早于探测总步数的 90%，说明暂定预算不够，把该库的 equivalent_epochs 改成探测值（IDRiD 2000、DDR 400）；否则保留暂定值。不取两库中较大的那个。
    规则修订（2026-10-08，两次，都是看过探测验证曲线之后做的，都没有读测试集）：
      第一次：原规则“最高点在后四分之一就翻倍”改为“落在最后 10% 才翻倍”。理由：poly 调度按探测的两倍步数展开，学习率退火在后半程才把曲线推高，所以最高点自然偏后，不能直接说明训练量不够。
      第二次：改用平滑后的最高点。理由：相邻两次验证常差 0.03 到 0.09，单个点的最高值受噪声支配。
    各次修订前后的判断都写在 00。
    决定只看训练和验证，不看测试。把四条曲线的最高点、所在步数和最终取值写进 00 的 “预算探测” 段，连同 bs_frozen.yaml 一起提交，然后才跑下一步。
11. bash bench/scripts/server_run.sh bs-seed0       B-std 种子 0，16 个任务
12. 读 B1 和 B-std 种子 0 的训练和验证曲线（bash bench/scripts/server_run.sh curves 'BS_*'）。没有问题，再写测试概率图并评测：
    bash bench/scripts/server_run.sh b1-score0
    bash bench/scripts/server_run.sh bs-score0
    启动器会先确认种子 0 的 recipe.json 与当前预算一致，不一致就拒绝。
13. bash bench/scripts/server_run.sh bs-rest        B-std 种子 1、2，28 个任务（H2Former 不在第一批）
11–13 合并（2026-10-08 起采用）：RETISEG_GPUS="2 3 4 5 6 7" bash bench/scripts/server_run.sh bs-queue
    一个启动器管住这几张卡，按顺序排三波：种子 0，种子 0 的测试概率图和评测，种子 1、2。某个模型在某个库上的后两波，要等这个模型在这个库上的种子 0 写出 diagnostic.json，而且预算签名与当前 bs_frozen.yaml 一致；这个种子 0 失败，它的后两波就不开，并记为失败。按模型分开等，是为了不让一个慢模型（FCT 在 DDR 上约 96 小时）拖住其他模型。卡上还有别的任务时，等它空出来再接：卡上有本用户的任何进程就算忙，别的用户的进程合计不少于 RETISEG_BUSY_MIB 才算忙。已完成或正在跑的任务跳过。
    与原顺序的差别：种子 0 的曲线不再等人工看过才打分、开后续种子，三波自动接上。曲线照常在种子 0 结束时看；发现问题就停掉启动器（只杀启动器进程，正在跑的训练不受影响），改完再重排。
    同一组卡上不要同时开两个启动器。

五、中断与恢复
所有训练命令都带 --resume。卡掉线、进程被杀以后，原样再执行同一阶段：已完成的任务跳过（seed0 看 diagnostic.json，打分阶段看 metrics_test.json），没完成的从 resume.pt 接着训，权重与不中断时逐位相同。resume.pt 只在验证时写，所以最多损失一次验证间隔。
预算改过以后不能续训：resume.pt 里记了预算签名，签名不一致时报错，此时删掉那个运行目录重跑。
同一波次还在跑时可以再提交一次（例如另开几张卡）：console.log 里有开始行、没有结束行、且该进程仍活着的任务会跳过。旧开始行（2026-10-07 之前）没有进程号，一律当作仍在运行；确认进程已死后加 RETISEG_IGNORE_RUNNING=1。
在一波还在跑时 git pull 是安全的：已在跑的任务不受影响，排在后面的任务启动时读新的 cell 和代码，environment.json 记的是它启动时的提交号。

六、记录管理
1. 代码和协议：每个正式阶段开始前，bench/ 必须已提交。server_run.sh 在有未提交改动时拒绝启动（RETISEG_ALLOW_DIRTY=1 可以强制，但会记成 dirty+allowed）。每个运行目录的 environment.json 记下提交号。
2. 阶段台账：runs/logs/stages.tsv，每启动一个阶段写一行：时间、阶段、提交号、工作区状态、日志路径、进程号。阶段日志在 runs/logs/<时间>_<阶段>.log。
3. 任务日志：每个任务的输出写在各自的 runs/<运行>/console.log，开头一行 “== start 波次 时间 gpu 卡号 host 主机 pid 进程号”，结尾一行 “== exit 退出码 时间”。
4. 总表：bash bench/scripts/server_run.sh status 打印所有运行的状态（running、failed、trained、scored），并写入 runs/status.tsv。测试 mAUPR 只在 metrics_test.json 已存在时显示。
5. runs/ 不进 Git。每个阶段结束后，把小文件拉回工作站备份（检查点和概率图留在服务器）：
   rsync -a --include='*/' --include='*.json' --include='*.jsonl' --include='*.log' --include='*.tsv' --include='*.yaml' \
     --exclude='*' SERVER:retiseg/runs/ runs/
6. 叙述记录：每个阶段的结论写进 00_进度.txt，一段一个日期，写清做了什么、看了哪些数、结论是什么、对应的提交号。改协议的决定（预算、批大小）写在 00，并与对应的配置一起提交。
7. 不允许的事：看过测试指标以后再改预算、增强或选择规则；在 runs/ 里手工删改 history.jsonl 或 recipe.json。
